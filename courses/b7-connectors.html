Wiring connectors

Until tonight, WorkBuddy could only see one folder: ~/Documents/Meridian. Connectors change that. They are pluggable tools and data sources - Google Drive, Gmail, Notion, Slack, GitHub, Jira, Confluence, plus web search - that the agent calls on demand, following the MCP pattern. You will wire exactly one, minimally, then run the first task in this course that pulls from two sources at once: a market report in Drive and this week's numbers on disk, merged into one Meridian update. And because every connector is a new data surface, you will revisit Data Management before you leave.

Where this session sits

Part 1 · covers workbuddy.ai docs "Connectors", Tencent Cloud capability guide

Pluggable tools the agent calls on demand 7 min live

A connector is not an import and not a sync. It is a live tool the agent can call during a task, when the plan needs it - "read that Drive folder", "search the Notion space", "check the Jira board". This is the MCP pattern: pluggable tools and data sources behind one standard interface, so the same instruction habits you built in b2 work unchanged - only the reachable world gets bigger. The documented set: GitHub, Jira, Confluence, Google Drive, Gmail, Notion, Slack, plus web search and the local file system you have been using since b1.

LiveWhich connector for which chore4 min▶

Map the connector to the task family it unlocks - this is your wiring menu, and the test for whether a connector deserves to exist on your machine:

  • Google Drive - the team's shared docs and sheets become reachable context for reports and analysis. The most common first wire for office work.
  • Gmail - summarize, extract, draft from the inbox. Highest value, most sensitive surface - wire it last, not first.
  • Notion - wikis and databases as source material; also a fine first wire if your team lives there instead of Drive.
  • Slack - pull thread context in; and in b8 it becomes the delivery channel scheduled tasks push to.
  • GitHub · Jira · Confluence - the engineering-adjacent trio: issues, tickets, team docs. Wire only if your recurring chore actually reads them.
  • Web search - already there, no account needed - it powered b4's research session.
Self-studyWhy "on demand" matters more than it sounds3 min read▶

Because a connector is a tool call inside the four-stage loop, it inherits every safeguard you already know: the plan shows which sources a task will touch before anything runs, and the audit trail records what was actually read. Read the plan with new eyes from tonight on - the question is no longer just "right files?" but "right sources?". If a plan reaches for Gmail on a task that only needed the Meridian folder, that is your cue to stop, not confirm. The gate from b1 does not move; the traffic through it grows.

Part 2 · covers Data Management docs, independent review notes on setup complexity

Reachable context grows - so does the data picture 6 min live

Two things happen with every wire, and they are not the same thing. First, the good one: your Context lever from b2 extends beyond your folders - instructions can now name a Drive folder or a Notion space the way they named local files, and results get better for the same reason scoped folders beat guessing. Second, the one to manage: the data picture changes per-connector. b1's honest selling point - the desktop app works on local files without a mandatory cloud upload - stops being the whole story the moment Drive or Gmail is wired. Cloud sources flow through cloud services. That is not a scandal; it is a fact you govern. The rule: every time you connect something, revisit Data Management.

⚠ Connector sprawl is folder sprawl at cloud scale In b1 you refused to authorize your whole home directory. Apply the identical discipline here: wire what a real, recurring task needs - nothing speculative. Every idle connector is reach you granted for no deliverable: a bigger surface in every plan you skim, a wider blast radius when an instruction is misread, and one more line in the data picture you are supposed to be able to explain. One chore, one connector. "Might be useful someday" is how boundaries die.
Self-studyHonesty rail: drift + first-time friction2 min read▶

Two honest edges, both documented. First, the connector list drifts - WorkBuddy is a fast-moving product (global launch May 2026), and the set named on this page is what the docs listed when this course was built. Re-verify the actual names in-app and at workbuddy.ai before you rely on any of them. Second, setup has real first-time complexity - independent reviews flag exactly this, and they are right: OAuth screens, scope pickers, and account choices take patience the first time. Budget an hour for your first wire, not ten minutes. The second connector takes a quarter of that.

Build-along 1 of 2 · the Slack/Google integrations practice case

Wire one connector, minimally ★ 12 min · everyone does it

Google Drive if your team lives in Docs and Sheets, Notion if it lives in a wiki - pick ONE. The point is the pattern, not the catalog.

Open Connectors in WorkBuddy's settings and pick Google Drive (or Notion). You will be handed to the provider's own authorization screen - this consent belongs to the provider, not to WorkBuddy.

Authorize minimally. Where the provider offers a scope choice, grant the narrowest that works - a single folder or space, read access, one account. This is b1's one-project rule crossing the dashed line.

Stage a test folder. In Drive, make a folder like Meridian-MY and drop in three real files - a doc, a sheet, anything genuinely yours. Real material, not toys, same as b1.

Run the digest task: "Summarize the three newest files in Drive:/Meridian-MY into one digest - one paragraph per file, plus one line on what they collectively say." Read the plan: it should name the Drive source explicitly. Confirm, then open the deliverable.

Close the loop: open Data Management and re-read it now that a cloud source is wired. Sixty seconds tonight; a standing habit forever.

Build-along 2 of 2 · Meridian running project

The cross-source task ★ 10 min · everyone does it

The first task in this course that no single source could answer - the real reason connectors exist. Meridian's market report (b4's artifact, now sitting in the shared Drive folder) meets this week's numbers in the local folder, in one instruction.

Stage the two sources. Put the b4 market report in Drive:/Meridian-MY; confirm this week's sales file is in ~/Documents/Meridian. Two sources, either side of the boundary.

Run the five-lever instruction: "Pull the Malaysia market report from Drive:/Meridian-MY and this week's sales numbers from ~/Documents/Meridian, and combine them into a one-page Meridian update for Monday's leadership sync: top three market signals from the report, this week's numbers against them, one recommendation. Verify every figure against its source file before delivering."

Read the plan as a sources list. It should show both the Drive read and the local read before anything runs. That is the b1 gate doing its new, bigger job.

Check the seams in the deliverable. Cross-source work fails at the joins - a report figure attributed to the sales file, or the reverse. Skim the audit trail for which source fed which claim. b2's currency trap taught you why: the S$102,947 vs S$89,715.03 disaster was two sources joined without a check.

Real world

This pattern is most office work. Brief in the wiki + numbers in a sheet; contract in Drive + terms in an email thread; ticket in Jira + spec in Confluence. "Two sources, one deliverable" is the shape of the job - which is exactly why the connector you wire should be the one your recurring version of this pattern actually needs.

Homework

Try it yourself - this week ◐ 30-40 min total

  • Name the one recurring chore from your real week that needs a source beyond your folders - then wire that connector and only that one, minimally scoped. If no chore needs one, wire nothing: that is a correct b7 result.
  • Run the cross-source pattern on your own files: one cloud source + one local file, one deliverable, verify ask included. Save the instruction - it is a template you will reuse weekly.
  • Open Data Management and write down, in one sentence per wired connector, where that data flows. If you cannot write the sentence, unwire it until you can.
  • Re-verify the connector names in-app against this page - the list drifts, and noticing the drift is part of the skill.

Check yourself

Three questions before you go 🎯 ◐ 90 seconds

1 · What is a connector, in the MCP-pattern sense this page teaches?

No copy, no mirror - a live tool call inside the four-stage loop. That is why the plan screen and the audit trail still cover it: connector reads show up as steps you approve and actions you can review.

2 · You wire Google Drive tonight. What must change in how you think about data?

Per-connector, not all-or-nothing. Local files stay local; the wired cloud source flows through its service. The habit: connect a source, open Data Management, re-read the picture.

3 · Which connector should you wire this week?

Connector sprawl is folder sprawl at cloud scale. One chore, one connector, minimal scope. And Gmail is the most sensitive surface - it goes last, behind a proven need, not first.
